### 3.2 Immunity window W and prior-hit subtraction (question a)

`LivingEntity.hurtServer` bytecode (`minecraft-merged.jar`), condensed:

```text
184: getfield invulnerableTime:I
189: ldc 10.0f
193: ifle 240                          // W test: only while invulnerableTime > 10
196: source.is(DamageTypeTags.BYPASSES_COOLDOWN)
203: ifne 240                          // bypass goes to the normal branch
206: fload_3; getfield lastHurt
212: ifgt 217                          // stronger than previous raw hit?
215: iconst_0; ireturn                 // no -> zero damage, no event
217: actuallyHurt(level, source, damage - lastHurt)
229: putfield lastHurt = damage
234: iconst_0; istore 8                // flag = false
...
240: lastHurt = damage; invulnerableTime = 20; actuallyHurt(level, source, damage)
258: hurtDuration = 10; hurtTime = hurtDuration
```

- **W = 10 server ticks.** A normal accepted hit sets `invulnerableTime = 20`. The counter is decremented once per server tick in `ServerPlayer.tick()` (or in `LivingEntity.baseTick()` for non-players) and the in-window branch applies while it is `> 10`, i.e. values 20 down to 11.
- **The previous raw hit is subtracted before mitigation.** The in-window path calls `actuallyHurt(level, source, damage - lastHurt)`, and only then does `actuallyHurt` apply `getDamageAfterArmorAbsorb`, `getDamageAfterMagicAbsorb`, and absorption. `lastHurt` stores the amount after shield/helmet blocking but before armour, magic and absorption.
- A hit in the window with `damage <= lastHurt` returns `false` and does nothing. Equality is rejected.
- The subtracted amount and `lastHurt` are the *raw* quantity; do not model the increment as already mitigated.

### 3.3 Damage types that bypass the cooldown (question b)

- The gate is `DamageSource.is(DamageTypeTags.BYPASSES_COOLDOWN)` (`DamageTypeTags` in the merged jar).
- **No vanilla damage type is in that tag in 26.2.** Neither `minecraft-client.jar`, `minecraft-server.jar`, `minecraft-extracted_server.jar` nor `minecraft-merged.jar` contains `data/minecraft/tags/damage_type/bypasses_cooldown.json`; the other 7 `bypasses_*` tag files are present. A missing tag is an empty tag.
- `is_explosion` contains `fireworks`, `explosion`, `player_explosion`, `bad_respawn_point` (verified from the authenticated client jar). None of them bypass the cooldown.
- Consequence: crystal, bed, anchor and respawn-point explosions all enter the in-window branch. A datapack or server-side mod may add entries at runtime; that is an unknown, not a client-side invariant.

### 3.4 Stronger in-window hit and damage events (question c)

- The in-window branch sets local flag 8 to `false` (offset 234).
- At offset 283 the code tests that flag and jumps over the block containing `ServerLevel.broadcastDamageEvent(this, source)` (offset 321), `markHurt` (offset 348) and `dealDefaultKnockback` (offset 362).
- Therefore, for a non-bypassing stronger in-window hit in this build: **no damage event broadcast**; additionally **no hurt animation, no hurt sound and no default knockback** from this hit. Death handling, `lastDamageSource`, effects' `onMobHurt` and advancement triggers still run, and `actuallyHurt` still changes health and absorption.
- Health and absorption metadata are sent later by the normal per-tick `ServerEntity` pass (§3.7), so tracking players see the numbers change without the hurt animation.
- This is a compiled-bytecode finding from a desk audit. It matches the technical review's warning that stronger hits "need not broadcast another normal damage event"; the knockback omission goes further than some older versions. **P0.3 must confirm it with a recorded trace. Until then, the motion model must assume an in-window hit may still cause knockback**, the conservative assumption for target envelopes and self bounds.

### 3.5 Mitigation and geometry

#### 3.5.1 CombatRules mitigation ratio (question d)

Signatures:

```text
public static float net.minecraft.world.damagesource.CombatRules.getDamageAfterAbsorb(
    net.minecraft.world.entity.LivingEntity, float, net.minecraft.world.damagesource.DamageSource, float, float)
public static float net.minecraft.world.damagesource.CombatRules.getDamageAfterMagicAbsorb(float, float)
```

The armor bytecode implements:

```text
f = 2 + toughness / 4
g = clamp(armor - damage / f, armor * 0.2, 20)
h = g / 25
h' = clamp(EnchantmentHelper.modifyArmorEffectiveness(level, weapon, entity, source, h), 0, 1)
out = damage * (1 - h')
```

`getDamageAfterMagicAbsorb(damage, protection)` returns `damage * (1 - clamp(protection,0,20)/25)`. Resistance is applied by `LivingEntity.getDamageAfterMagicAbsorb` as a separate linear factor.

**Finding: under fixed armour, toughness, protection and damage source, the damage-to-input ratio is nondecreasing.** As `damage` rises, `armor - damage/f` falls until it reaches the `0.2 * armor` floor, so `h` is nonincreasing and `1 - h` is nondecreasing; the magic factor is constant for fixed protection. Composition of nondecreasing factors stays nondecreasing. This is a mathematical inference from the pinned formula, not a proof across state changes: armour durability (`hurtArmor` runs first), effect expiry, armour breakage, bypass tags, difficulty scaling in callers and server plugins can all change the function between hits.

Note that absorption is applied *after* these methods in `actuallyHurt` and never changes the ratio; do not subtract it inside the mitigation model.

#### 3.5.2 Explosion entity search and knockback (question f)

`ServerExplosion.hurtEntities` (`minecraft-merged.jar`):

- `diameter = radius * 2`; a power-6 crystal has `radius = 6`, so the **entity search extends 12 blocks** (AABB from `center ± (12 + 1)`, floored).
- Per entity: `ignoreExplosion` skip; `d = sqrt(distanceToSqr(center)) / 12`; if `d > 1` skip.
- Damage: `ExplosionDamageCalculator.getEntityDamageAmount` computes `impact = (1 - d) * seenPercent` and `damage = ((impact² + impact) / 2 * 7) * (2 * radius) + 1` (so ×12 for crystals). Exposure comes from `ServerExplosion.getSeenPercent`, which raycasts with `ClipContext.Block.COLLIDER`/`Fluid.NONE` — any collision shape blocks a sample, independent of blast resistance.
- Knockback: direction is `normalize(eyePosition - center)` for non-TNT entities (`position` for TNT); magnitude is `(1 - d) * seenPercent * knockbackMultiplier * (1 - EXPLOSION_KNOCKBACK_RESISTANCE)`, then `entity.push(vector)`.
- **The vector is three-dimensional and includes the vertical component. There is no two-block-hole, feet-level or zero-knockback exemption in the inspected code.** Only explosion-knockback resistance, spectator and creative-flying handling alter it.
- Do not use a 6-block knockback cutoff and do not assume a surrounded target stays in place.

#### 3.5.3 Crystal placement validity (question g)

`EndCrystalItem.useOn(UseOnContext)`:

1. Base block at clicked pos must be `Blocks.OBSIDIAN` or `Blocks.BEDROCK`, else `InteractionResult.FAIL`.
2. The block at `pos.above()` must satisfy `LevelReader.isEmptyBlock`, which is `getBlockState(pos).isAir()` — **strict air**, not "replaceable". Only the first block above the base is tested for air.
3. Entities: `level.getEntities(null, new AABB(x, y, z, x+1, y+2, z+1)).isEmpty()` is required. The entity volume is one block wide and **two blocks high**, starting at the base-top cell.
4. On a `ServerLevel`, an `EndCrystal` is constructed at `(x+0.5, y, z+0.5)`, `setShowBottom(false)`, added, `ENTITY_PLACE` game event fired, and the dragon fight `tryRespawn()` called; one item is consumed.

Consequence: a two-air-block placement rule is a stricter project profile, not the vanilla rule. The plan's placement predicate must model both the strict-air first cell and the 1×2×1 entity overlap, including the placing player.

### 3.6 Crystal lifecycle, explosion and attack packets

#### 3.6.1 `EndCrystal.hurtServer` for explosion-tagged damage (question e)

Signature: `public final boolean EndCrystal.hurtServer(ServerLevel, DamageSource, float)`.

Condensed behaviour from bytecode:

```text
if isInvulnerableToBase(source) -> false
if source.getEntity() instanceof EnderDragon -> false
if !isRemoved():
    remove(Entity.RemovalReason.KILLED)
    if !source.is(DamageTypeTags.IS_EXPLOSION):
        ds = source.getEntity() != null ? damageSources().explosion(this, source.getEntity()) : null
        level.explode(this, ds, null, x, y, z, 6.0f, false, Level.ExplosionInteraction.BLOCK)
    onDestroyedBy(level, source)
return true
```

- **Explosion-tagged damage removes the crystal and does not create a secondary crystal explosion.**
- Non-explosion damage (player attack, arrow, direct hit) removes it and creates a power-6, non-fire, block-interacting explosion attributed to the crystal and the causing entity.
- The explosion source's tag set is `is_explosion` = `fireworks`, `explosion`, `player_explosion`, `bad_respawn_point`.
- `kill(ServerLevel)` calls `onDestroyedBy` and the base kill without any explosion.
- Piston/direct combat attribution must distinguish "crystal removed by someone else's explosion, no secondary blast" from "crystal attacked and exploded".

#### 3.6.2 Attack/interact packet split and disconnect targets (question h)

26.2 has separate packets and handlers:

```text
net.minecraft.network.protocol.game.ServerboundAttackPacket(int entityId)   // record
net.minecraft.server.network.ServerGamePacketListenerImpl.handleAttack(ServerboundAttackPacket)
net.minecraft.network.protocol.game.ServerboundInteractPacket(int entityId, InteractionHand, Vec3, boolean)
net.minecraft.server.network.ServerGamePacketListenerImpl.handleInteract(ServerboundInteractPacket)
```

`handleAttack` order:

1. `PacketUtils.ensureRunningOnSameThread`; return if client not loaded or player spectator.
2. `level.getEntityOrPart(id)`; if null or outside the world border, return silently.
3. `player.isWithinAttackRange(stack, box, 3.0)` must pass, else return.
4. Return if the held stack has `DataComponents.PIERCING_WEAPON`.
5. **Disconnect** with `multiplayer.disconnect.invalid_entity_attacked` and a warning log if the target is an `ItemEntity`, an `ExperienceOrb`, the player themself, or an `AbstractArrow` whose `isAttackable()` is false.
6. Return if the item is disabled for the level's feature flags, or `cannotAttackWithItem(stack, 5)`.
7. `player.attack(entity)`.

`handleInteract` in the same build contains no equivalent invalid-target disconnect.

Consequence: a wrong but live entity ID is a real attack with no disconnect; only items/XP/self/non-attackable arrows trigger the disconnect. That is exactly why hard rule 4 cannot be relaxed by "the server only disconnects on bad IDs".

`MultiPlayerGameMode.startPrediction(ClientLevel, PredictiveAction)` is **private** in the authenticated vanilla class; Meteor widens it with `accessible method ... startPrediction` in `meteor-client.classtweaker`. Meteor's `CrystalAura` and `PacketMine` call it. Comet code may only rely on it through the audited Meteor capability, not as a vanilla public API.

### 3.7 Player health and absorption visibility (question i)

- Health: `LivingEntity.setHealth(float)` clamps to `[0, getMaxHealth()]` and writes `DATA_HEALTH_ID` (`SynchedEntityData.set`).
- Absorption: `LivingEntity.setAbsorptionAmount(float)` is final and calls the virtual `internalSetAbsorptionAmount(float)`. `Player` overrides it to write `DATA_PLAYER_ABSORPTION_ID`. Non-player living entities keep absorption only as a server-side field (no accessor in `LivingEntity`).
- Transport: `ServerEntity.sendChanges()` runs every server tick and calls `sendDirtyEntityData()`, which takes `SynchedEntityData.packDirty()` and sends `ClientboundSetEntityDataPacket(entityId, values)` through `ServerEntity.Synchronizer.sendToTrackingPlayersAndSelf`.
- **Both player health and player absorption are therefore sent to tracking players and to the player themself.** `actuallyHurt` writes absorption before health, so when both change in one tick they normally travel in the same packet; that is not a transaction guarantee across ticks, and unrelated healing/absorption refills can interleave. Read both fields from the same received list, keep a coherent effective-health snapshot, and never treat one field's presence as proof of the other's freshness.
- Server plugins can conceal or rewrite metadata; represent this as a capability with known/unknown/censored states rather than an invariant.
- **P0.3 obligation (C19):** record whether health and absorption arrive in one `ClientboundSetEntityDataPacket` when both change in the same tick. Until recorded, treat them as separate observations.

### 3.8 Meteor build 35 internals

#### 3.8.1 `PacketEvent.Receive` timing and thread (question j)

Source: `meteordevelopment/meteorclient/mixin/ConnectionMixin.java:47-53` in the authenticated sources jar.

```java

    at = @At(value = "INVOKE",
        target = "Lnet/minecraft/network/Connection;genericsFtw(Lnet/minecraft/network/protocol/Packet;Lnet/minecraft/network/PacketListener;)V",
```

- Posting happens **before** `Connection.genericsFtw`, i.e. before vanilla dispatches the decoded packet to its listener, and on the **Netty event-loop thread**, not the client thread.
- `ClientboundBundlePacket` is unpacked by Meteor itself: each sub-packet is posted individually and a cancelled sub-packet is removed from the iterator; the bundle wrapper is not posted.

- An enqueued observation is therefore **not** an applied world mutation. Meteor's own `InventoryWeaponAttack` documents this: "Receive runs on the network thread. Only inspect immutable packet data here."

#### 3.8.2 `DamageUtils` default and custom raycast (question j)

Source: `meteordevelopment/meteorclient/utils/entity/DamageUtils.java`.

```java
public static final RaycastFactory HIT_FACTORY = (context, blockPos) -> {
    BlockState blockState = mc.level.getBlockState(blockPos);
    if (blockState.getBlock().getExplosionResistance() < 600) return null;   // transparent
    return blockState.getCollisionShape(mc.level, blockPos).clip(context.start(), context.end(), blockPos);
};
```

- Default policy: blocks with explosion resistance below 600 are ignored entirely; obsidian (1200) and bedrock (3,600,000) block. This is a deliberate approximation, **not** vanilla exposure: vanilla `ServerExplosion.getSeenPercent` clips against every collider regardless of resistance. Meteor therefore overestimates exposure/damage behind soft cover.
- Public extension point: `DamageUtils.explosionDamage(target, targetPos, targetBox, explosionPos, power, RaycastFactory)` and `crystalDamage(..., RaycastFactory)` accept a custom `RaycastFactory` (`BiFunction<ExposureRaycastContext, BlockPos, BlockHitResult>`). `getOverridingHitFactory(BlockPos, BlockState)` substitutes a virtual block state at one position.
- Raw crystal damage uses the vanilla shape `((impact² + impact) / 2 * 7 * 12 + 1)` but casts to `int` before reductions; `calculateReductions` applies difficulty scaling, `CombatRules.getDamageAfterAbsorb` with floored armour, resistance and protection, and does not subtract absorption.
- Use distinct audited factories: faithful collision for estimates, conservative transparent/opaque variants for target lower bounds and self/friend upper bounds. Treat the returned value as an estimate with explicit assumptions, never as a server guarantee.
- **P1.2 obligation (C18):** the int truncation can understate damage. Compute unrounded values, or round self/friend upper bounds up.

Phase 2b must add project-owned post-handler hooks (or a single client-thread packet barrier) for those observations; `PacketEvent.Receive` alone is pre-application and on the network thread.

#### 3.10.3 Explosion block destruction by blast resistance (plan 0.1.6)

From `ServerExplosion.calculateExplodedPositions` and `ExplosionDamageCalculator`:

- Initial ray intensity is `radius * (0.7 + 0.6 * randomNextFloat())`.
- The ray advances in steps of about 0.3 blocks; each non-air block subtracts `(resistance + 0.3) * 0.3` from the intensity, where `resistance = max(Block.getExplosionResistance(), FluidState.getExplosionResistance())` (`ExplosionDamageCalculator.getBlockExplosionResistance` returns `Optional.empty()` for air with empty fluid, so air costs nothing).
- A position is added to the destroyed set while intensity stays `> 0` and `shouldBlockExplode(...)` is true; the default `shouldBlockExplode` returns `true`.
- With power 6 the initial intensity is 4.2–7.8, so a single obsidian (1200) step subtracts about 360 and stops the ray immediately; low-resistance blocks accumulate.
- `ServerExplosion.interactWithBlocks` then applies the block-explosion effects and drops according to the `ExplosionInteraction`; the crystal path passes `Level.ExplosionInteraction.BLOCK` with `fire = false`.
- This is separate from entity exposure: `getSeenPercent` clips against collision shapes without consulting blast resistance (§3.5.2).

#### 3.10.4 Piston push of end crystals (plan 0.1.10)

- `EntityTypes.END_CRYSTAL` is built with `sized(2.0f, 2.0f)`, `fireImmune()`, client tracking range 16, and `updateInterval(Integer.MAX_VALUE)`.
- `EndCrystal` does not override `Entity.getPistonPushReaction`, whose default is `PushReaction.NORMAL`; the entity is constructed with `blocksBuilding = true`.
- `PistonMovingBlockEntity` constants: `TICKS_TO_EXTEND = 2`, `TICK_MOVEMENT = 0.51`, `PUSH_OFFSET = 0.01`.
- `moveCollidedEntities` builds the moving block's collision shape, translates it by the current progress, expands the area forward by the movement delta (`PistonMath.getMovementArea`), queries `Level.getEntities(null, area)`, and for entities with a push reaction moves each by `min(movement, available) + 0.01` along the push direction through `moveEntityByPiston`, which calls `Entity.move(MoverType.PISTON, vector)` with a direction-specific NOCLIP thread-local set, then `applyEffectsFromBlocks`.
- Movement is therefore up to **0.51 + 0.01 blocks per tick for 2 ticks** during extension, clamped to the swept movement area; other block collisions still apply (only the moving block is bypassed by NOCLIP).
- Sticky retraction (`moveStuckEntities`) only affects entities matching the sticky criteria; an end crystal is not attached, so retraction does not pull it.
- **Observability caveat:** the crystal entity type's `updateInterval` is `Integer.MAX_VALUE`, so ordinary periodic position sync is effectively suppressed; the client receives an update only through an explicit `syncPosition`, dirty-data path, or the forced periods (`FORCED_POS_UPDATE_PERIOD = 60`, `FORCED_TELEPORT_PERIOD = 400`). Phase 0.4 must record exactly which position updates a pushed crystal produces; do not assume continuous tracking.

#### 3.10.5 `PlayerUtils` (plan 0.1.12)

`meteordevelopment/meteorclient/utils/player/PlayerUtils.java`: `getHorizontalVelocity(double)`, `centerPlayer()`, `canSeeEntity(Entity)`, `calculateAngle(Vec3)`, `shouldPause(boolean,boolean,boolean)`, `isMoving()`, `isSprinting()`, `isInHole(boolean)`, `possibleHealthReductions()`, `possibleHealthReductions(boolean,boolean)`, `distance`/`distanceTo`/`squaredDistanceTo`/`squaredDistance`/`isWithin` overloads, `distanceToCamera(double,double,double)`. `possibleHealthReductions` is an estimate for pause decisions, not a safety bound.

## 6. Residual uncertainty and open questions

1. **Plan v2.1 is recovered and committed** (`281ad4c`). The 0.1/0.2 diff is complete (§0.1, §3.10, §5.1); the C17 exceptions are in the plan's Hard invariants. Nothing remains blocked on the plan.
2. All Minecraft findings are bytecode inspections of the pinned release. Server plugins, datapacks and modified servers can change behaviour; runtime confirmation on an authorised local server belongs to a later phase.
3. The in-window "no knockback / no broadcast" result (C6) is unusual enough to deserve an explicit runtime test before it is encoded in the motion model.
4. `bypasses_cooldown` is empty only for vanilla data. In multiplayer the server's datapack tags are synchronised to the client, so bypass is a server-controlled unknown; do not encode "no bypass" as a client invariant.
5. Meteor `calculateReductions` is an estimate with its own assumptions (difficulty scaling, floored armour, resistance/protection ordering). It is not the server's arithmetic; keep the raw and mitigated quantities separate.
6. Coyduck was created 2026-10-18 and is very new; its provenance beyond the repository metadata was not established in this phase.
7. THM's non-CrystalAura history was not audited. The 0.2 decision keeps THM on the user's clarification that it is not the flagged project; Lambda is recorded as the true upstream, and any borrowing must pass the dual THM+Lambda attribution and GPL check in §5.2.
8. P0.3's two audit obligations (C6 knockback trace, C19 one-packet observation) and P1.2's rounding obligation (C18) are recorded here but **not executed** in this phase.
9. The processing barrier has no client-visible acknowledgement (C20). Phase 0.4 must define the observable server effect that stands in for it; until then, safety rule 3's barrier is unproven.
10. Crystal position sync is suppressed by `updateInterval = Integer.MAX_VALUE`. Phase 0.4 must record every position update a piston push actually produces, including whether the client ever learns the final pushed position.
11. Proposed plan wording for C6, C16, C18 and C20 is recorded in §0 but not applied; only the C17 exceptions were inserted into the plan in this update.
