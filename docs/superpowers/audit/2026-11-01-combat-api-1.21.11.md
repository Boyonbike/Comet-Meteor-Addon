### 3.2 `LivingEntity.hurtServer` — W, raw-before-mitigation, bypass types, stronger in-window hit

Source of truth: `javap -c -p net.minecraft.world.entity.LivingEntity` from NM (`171dacfde929df4e`). The 26.2 audit's C4/C6/C19 are re-verified; the only code-shape change is that 1.21.11 inlines the default knockback as the 3-arg `knockback(0.4, dx, dz)` (like 26.1.2), not 26.2's `dealDefaultKnockback`.

Exact `hurtServer(ServerLevel level, DamageSource source, float damage)` control flow with bytecode offsets:

1. `isInvulnerableTo(level, source)` → return false (0–10); `isDeadOrDying()` → return false (11–19); `IS_FIRE` + fire resistance → return false (20–41); sleeping → `stopSleeping()` (42–52); `noActionTime = 0` (53–57).
2. `damage = max(0, damage)` (58–65); save original in local 4 (66); `getUseItem()` → local 5 (69–73); `applyItemBlocking(level, source, damage)` → local 6 (75–82); `damage -= blocked` (84–88); `itemBlocked = blocked > 0` → local 7 (89–101).
3. `IS_FREEZING` + `FREEZE_HURTS_EXTRA_TYPES` → `damage *= 5` (103–131); `DAMAGES_HELMET` + damaged helmet → `damage *= 0.75` (132–166); NaN/Infinite → `Float.MAX_VALUE` (167–184).
4. `boolean flag = true` (185–186, local 8). **Window test (188–197): `invulnerableTime > 10.0f`** — exactly W = 10. `BYPASSES_COOLDOWN` (200–207) jumps to the normal branch.
5. In-window: `damage <= lastHurt` → return false (210–220; equal rejected). Otherwise `actuallyHurt(level, source, damage - lastHurt)` (221–230) — **the previous raw, post-blocking, pre-armour value is subtracted before mitigation** — then `lastHurt = damage` (233–235), `flag = false` (238–239).
6. Normal branch (244–274): `lastHurt = damage`; `invulnerableTime = 20`; `actuallyHurt(level, source, damage)`; `hurtDuration = 10`; `hurtTime = hurtDuration`.
7. `resolveMobResponsibleForDamage` / `resolvePlayerResponsibleForDamage` (276–286). **`iload 8; ifeq 480` (287–289)** — if flag is false, skip the entire post-hit block to offset 480.
8. Flag-true block (292–480): if `itemBlocked` and `DataComponents.BLOCKS_ATTACKS` present → `BlocksAttacks.onBlocked` (305–322), else `ServerLevel.broadcastDamageEvent(this, source)` (325–331); `markHurt()` unless `NO_IMPACT` and not (blocked and damage ≤ 0) (331–355); unless `NO_KNOCKBACK`, the default knockback is inlined — for projectiles `calculateHorizontalHurtKnockbackDirection` (negated), else source-position-minus-this direction, then **`knockback(0.4, dx, dz)`** (456–466); then unless `itemBlocked`, `indicateDamage(dx, dz)` (472–477).
9. Death handling, `checkTotemDeathProtection` (480–536), `lastDamageSource`/`lastDamageStamp` (554–572), `MobEffectInstance.onMobHurt` loop (575–617), advancement triggers (620–718).

Consequences (RE-VERIFIED, not inferred):

- **W = 10** is a threshold on the remaining invulnerability counter, not a duration; counter set to 20 on a normal hit and decremented once per server tick, so a hit within 10 ticks is in-window.
- **Raw-before-mitigation subtraction**: the subtracted value is post-blocking, post-freezing, post-helmet, but **before** armour, enchantment protection, resistance and absorption.
- **No vanilla damage type has `BYPASSES_COOLDOWN`**: `bypasses_cooldown.json` is absent from NM and the authenticated client jar (34 tag JSONs present, none `bypasses_cooldown`).
- **Stronger in-window hit** still writes health/absorption via `actuallyHurt`, but skips damage-event broadcast, `markHurt`, hurt sound/animation and default knockback (C6). Whether the target moves zero blocks on 1.21.11 is a runtime question (§6).
- `actuallyHurt` order: `getDamageAfterArmorAbsorb` → `getDamageAfterMagicAbsorb` (resistance then protection enchantment) → `max(damage − absorption, 0)` → `setAbsorptionAmount(absorption − (raw − damage))` → return if damage 0 → combat tracker / `setHealth(getHealth() − damage)` / hurt effects. For players, `setAbsorptionAmount` writes `Player.DATA_PLAYER_ABSORPTION_ID`; health uses `LivingEntity.DATA_HEALTH_ID`.

Damage-type tag contents in NM (`data/minecraft/tags/damage_type/`): `bypasses_effects.json` = `[starve]`; `bypasses_enchantments.json` = `[sonic_boom]`; `bypasses_resistance.json` = `[out_of_world, generic_kill]`; `bypasses_invulnerability.json` = `[out_of_world, generic_kill]`; `bypasses_armor.json` includes `on_fire, in_wall, cramming, drown, fly_into_wall, generic, wither, dragon_breath, starve, fall, ender_pearl, …`; `is_explosion.json`, `no_knockback.json`, `is_player_attack.json`, `mace_smash.json`, `bypasses_wolf_armor.json` present. `BYPASSES_COOLDOWN` has no JSON, so the tag is empty in vanilla.

### 3.3 `CombatRules` mitigation monotonicity

`CombatRules` (`88d29ee3cc0f3106`) constants: `MAX_ARMOR = 20.0f`, `ARMOR_PROTECTION_DIVIDER = 25.0f`, `BASE_ARMOR_TOUGHNESS = 2.0f`, `MIN_ARMOR_RATIO = 0.2f`, `NUM_ARMOR_ITEMS`.

`getDamageAfterAbsorb(LivingEntity entity, float damage, DamageSource source, float armor, float toughness)`:
```
f          = 2 + toughness / 4
armorRatio = clamp(armor - damage / f, armor * 0.2, 20)
e          = armorRatio / 25
if (source.getWeaponItem() != null && level instanceof ServerLevel)
    e = clamp(EnchantmentHelper.modifyArmorEffectiveness(level, weaponItem, entity, source, e), 0, 1)
return damage * (1 - e)
```
`getDamageAfterMagicAbsorb(float damage, float protection)` = `damage * (1 - clamp(protection, 0, 20) / 25)`.

**Monotonicity.** For fixed entity/source/armour/toughness, `armorRatio` is non-increasing in `damage` (the `−damage/f` term lowers it until the `0.2·armor` floor), so `e` is non-increasing and `1 − e` is non-decreasing; `damage · (1 − e)` is strictly increasing in `damage` across both clamp boundaries. The magic-absorb step and resistance step multiply by constants for a fixed effect state. The only non-constant hook is `EnchantmentHelper.modifyArmorEffectiveness`, which depends on the weapon (not the damage value) in vanilla; hold the source/weapon fixed when comparing the ratio. **Mitigation is nondecreasing in input damage; no inversion found.**

### 3.4 `ServerExplosion` — entity search, damage, 3-D knockback, block destruction

`ServerExplosion` (`5ecc7043423228f5`), `ExplosionDamageCalculator` (`e7ec06b507fbc0e3`), `Explosion` (`5cab37100afe34d8`). The algorithm is identical to 26.x.

**Entity search and damage** (`hurtEntities`, private):

- `if (radius < 1.0E-5) return;` then **`float f = radius * 2`** (offsets 12–18). For power 6 that is **12 blocks**: the AABB is `Mth.floor(center ± f ± 1)` on each axis; each candidate is rejected when `sqrt(distanceToSqr(center)) / f > 1`.
- Candidate position `PrimedTnt ? position() : getEyePosition()`; direction = normalize(position − center).
- `shouldDamageEntity` (no line-of-sight gate), `getKnockbackMultiplier`, `seen = getSeenPercent(center, entity)`.
- Damage `entity.hurtServer(level, source, getEntityDamageAmount(...))`; `getEntityDamageAmount`: `f = radius*2`, `d = sqrt(distanceToSqr(center))/f`, `impact = (1−d)·seen`, `return (impact*impact + impact)/2 * 7 * f + 1` — power 6 max point-blank full-exposure = 85.
- Knockback: `resistance = LivingEntity ? getAttributeValue(EXPLOSION_KNOCKBACK_RESISTANCE) : 0`; `entity.push(dir.scale((1−d) · seen · knockbackMult · (1−resistance)))` (offsets 395–404) — **all three components**, so genuinely 3-D. `getSeenPercent` (`public static`, offsets 0–…): `xStep = 1/((maxX−minX)·2+1)` (same y/z), offsets `(1 − floor(1/step)·step)·0.5`, one ray per sample from the sample to the centre, `level.clip(...)`; returns hit fraction.

**Block destruction** (`calculateExplodedPositions`, private): 16×16×16 direction shell; per ray `intensity = radius · (0.7f + level.random.nextFloat() · 0.6f)` (power 6 → 4.2 … 7.8); step length ~0.3; each non-air block subtracts `(resistance + 0.3) · 0.3` (air costs nothing); a position is destroyed while `intensity > 0 && shouldBlockExplode(...)` (default true). Obsidian (1200) stops a ray immediately; low-resistance blocks accumulate. `ExplosionDamageCalculator.getBlockExplosionResistance` returns empty for air/empty fluid.

### 3.6 Attack handler, server health/absorption tracking, ack, entity status, respawn

## 4. Concise answers (a–l), mirroring the 26.2 audit

**a. Is the cooldown window W = 10 server ticks, and is the earlier hit subtracted raw, before mitigation?**
Yes. In `LivingEntity.hurtServer(ServerLevel, DamageSource, float)` (NM, offsets 185–274) the server sets `flag = true`, enters the in-window branch only when `invulnerableTime > 10` and the type lacks `BYPASSES_COOLDOWN`; in that branch `damage <= lastHurt` returns false (equal rejected); otherwise `actuallyHurt(level, source, damage - lastHurt)` — the subtraction is on the raw, post-blocking, pre-armour value — then `lastHurt = damage`, `flag = false`. The normal branch sets `lastHurt = damage`, `invulnerableTime = 20`, `actuallyHurt(level, source, damage)`, `hurtDuration = 10; hurtTime = 10`. (§3.2)

**b. Does any vanilla damage type bypass the cooldown?**
No. `data/minecraft/tags/damage_type/bypasses_cooldown.json` is **absent** from the 1.21.11 client/server/merged jars (34 tag JSONs present, none named `bypasses_cooldown`). `DamageTypeTags.BYPASSES_COOLDOWN` exists but the tag is empty in vanilla; only datapacks/mods can populate it. (§3.2)

**c. What does a stronger in-window hit do beyond health?**
After `actuallyHurt(damage - lastHurt)` at 221–230, `flag = false` (238–239) and `iload 8; ifeq 480` (287–289) skips the whole post-hit block: no `ServerLevel.broadcastDamageEvent` (325–331), no `markHurt` (352), no default knockback (456–466), no `indicateDamage` (472–477). Health/absorption still change via `actuallyHurt`. Re-verified statically; the 26.2 runtime trace is not 1.21.11 evidence (§6). (§3.2)

**d. Is damage monotone in the input under `CombatRules`?**
Yes, for fixed armour/toughness/protection/source. `f = 2 + toughness/4`; `armorRatio = clamp(armor − damage/f, armor·0.2, 20)`; `e = armorRatio/25`; output `damage·(1−e)`, with a constant magic-absorb/resistance factor. `armorRatio` is non-increasing in damage, so `1−e` is non-decreasing and the product strictly increases; continuous at the clamp boundary. (§3.3)

**e. Does a power-6 crystal blast tagged `is_explosion` remove the crystal without a secondary explosion?**
Yes. `EndCrystal.hurtServer` (offsets 22–101) removes `KILLED`, then `if (!source.is(IS_EXPLOSION))` builds `damageSources().explosion(this, source.getEntity())` (or null) and calls `level.explode(this, ds, null, x, y, z, 6.0f, false, Level.ExplosionInteraction.BLOCK)`; an explosion-tagged hit skips that call and runs `onDestroyedBy` only. (§3.5)

**f. How far does the explosion search, and is the knockback 3-D?**
`ServerExplosion.hurtEntities` uses `float f = radius * 2` (offsets 12–18), so power 6 searches a 12-block radius (AABB `floor(center ± f ± 1)`); `d = sqrt(distanceToSqr(center))/f`, skip if `> 1`. `entity.push(dir.scale((1−d)·seen·mult·(1−resistance)))` includes the Y component; `seen` comes from `getSeenPercent` (ray-clips the bounding box). No line-of-sight gate; cover reduces `seen`. (§3.4)

**g. What exactly does crystal placement require?**
`EndCrystalItem.useOn`: clicked block must be `Blocks.OBSIDIAN` or `Blocks.BEDROCK`; `above = pos.above()` must be strictly air (`isEmptyBlock`); the 1×2×1 AABB `(x, y, z, x+1, y+2, z+1)` must contain no entities; server spawns `EndCrystal(level, x+0.5, y, z+0.5)`, `setShowBottom(false)`, `addFreshEntity`, `GameEvent.ENTITY_PLACE`, dragon-fight `tryRespawn`, `shrink(1)`. The second block is not checked for air separately (only the entity AABB). (§3.5)

**h. Which attacks does the server disconnect for?**
`ServerGamePacketListenerImpl$1.onAttack()` disconnects with `multiplayer.disconnect.invalid_entity_attacked` for `ItemEntity`, `ExperienceOrb`, `== player`, or `AbstractArrow` with `!isAttackable()`. Before that (`handleInteract`) it requires `hasClientLoaded`, target inside the world border, and `packet.isWithinRange(player, box, 3.0)`; after it requires `stack.isItemEnabled(...)` and `!cannotAttackWithItem(stack, 5)`. There is no `PIERCING_WEAPON` gate (26.2's `handleAttack` had one). (§3.6)

**i. How are health and absorption tracked and sent by the server?**
Two separate fields: `LivingEntity.DATA_HEALTH_ID` (statically id 9) and `Player.DATA_PLAYER_ABSORPTION_ID` (statically id 15). `ServerEntity.sendDirtyEntityData()` packs dirty values into one `ClientboundSetEntityDataPacket` to tracking players **and self**; `ServerPlayer.doTick()` separately sends `ClientboundSetHealthPacket`. Whether one damage tick batches both health and absorption in one entity-data packet is UNCONFIRMED for 1.21.11 (§6). The client applies health via `LocalPlayer.hurtTo` and metadata via `assignValues`. Adapters use the accessor constants. (§3.6)

**j. Is Meteor's `PacketEvent.Receive` before or after vanilla, and on which thread?**
Before vanilla, on the Netty thread. Build 82 `ClientConnectionMixin.onHandlePacket` injects `Connection.channelRead0` at `INVOKE Connection.genericsFtw` `shift=BEFORE`; bundle sub-packets get one Receive each (removable); the wrapper is not posted; a cancelled non-bundle packet cancels vanilla handling. `DamageUtils.HIT_FACTORY` treats blocks with resistance < 600 as transparent and its `RaycastFactory` is public; its damage is cast to `int` at line 95 with a hard-coded `12`. (§3.8)

**k. What does Meteor's `CrystalAura` send, and when?**
Build 82: the attack path funnels to **line 873 `mc.player.networkHandler.sendPacket(PlayerInteractEntityC2SPacket.attack(entity, mc.player.isSneaking()))`** (Mojmap `ServerboundInteractPacket.createAttackPacket`) — direct, no `startPrediction`. The place path funnels to **line 1039 `mc.interactionManager.sendSequencedPacket(mc.world, (sequence) -> new PlayerInteractBlockC2SPacket(hand, result, sequence))`** (Mojmap `MultiPlayerGameMode.startPrediction` + `ServerboundUseItemOnPacket`). There is also a spawn/fast-break path (`onEntityAdded` line 721 → `doBreak(event.entity)` line 732 → `attackCrystal`). Four `Rotations.rotate(DDIRunnable)` call sites (`onPreTickLast`, `doBreak(Entity)`, `doYawSteps`, `lambda$doPlace$19`); callbacks run later in `Rotations.onSendMovementPacketsPost` line 131, so a callback queued before suppression can still send (queued-callback hazard). Suppression surface: eight HEAD cancels, both rotate `@Redirect`s wrapping `CrystalCombatGate.guard`, and `protects(UUID)` on `doBreak(Entity)`/`attackCrystal`; `placeCrystal` HEAD is the place-side cancel point (covers the direct line-994 branch and the line-1071 self-recursion); do **not** cancel `onEntityAdded`. (§3.8)

**l. Do the Comet helpers send packets, and who owns what?**
`InventorySlotLoan.prepare()` **can send** (`handleInventoryMouseClick(..., ClickType.SWAP, ...)` lines 83/130); `InventoryWeaponAttack.onTick` **can send** (`mc.gameMode.attack` + swing); `Speedmine.requestBreak` **can send** (`ServerboundPlayerActionPacket.START_DESTROY_BLOCK`, no cancel/owner token); `ScaffoldCoordinator` observes only; `PlacementTracker`/`ServerPacer`/`PacketBudget` are pure. Ownership unchanged: Meteor owns the offhand and the rotation queue; the scaffold adapter refuses while `Rotations.rotating` or the accessor queue is non-empty. The port must not call `prepare()`, `Speedmine.requestBreak` or the `InventoryWeaponAttack` tick from a send-forbidden path (C17). (§3.9)

## 6. Residual uncertainty

1. **Metadata numeric ids.** Static derivation for 1.21.11 (identical accessor counts to 26.1.2: `Entity` 8, `LivingEntity` 7, `Player` 4) gives `DATA_HEALTH_ID` = 9 and `DATA_PLAYER_ABSORPTION_ID` = 15. The 26.2 audit's trace reported absorption id 17, which does not match; the numeric id is **UNCONFIRMED** for 1.21.11 and the port must key on the accessor objects (already done in `EntityDataIds`).
2. **Runtime behaviour of the stronger in-window hit.** The static bytecode is unambiguous (no broadcast/markHurt/knockback; health+absorption still written), but no 1.21.11 trace exists. The 26.2 trace (zero target movement) is not 1.21.11 evidence; Phase 0.4 must record it locally.
3. **Server packet ordering for self damage.** `ServerEntity.sendDirtyEntityData()` and `ServerPlayer.doTick()` can both emit in one tick; the relative order of `ClientboundSetEntityDataPacket` (health/absorption) and `ClientboundSetHealthPacket` is not established from bytecode. The one-packet obligation (C19) remains UNCONFIRMED.
4. **Piston displacement per tick.** Constants `TICK_MOVEMENT = 0.51` + `PUSH_OFFSET = 0.01` are identical to 26.x, but the actual per-tick displacement on 1.21.11 was not traced (the 26.2 trace measured 1.02 blocks over two ticks, not the literal 1.04).
5. **Meteor event timing for `EntityDestroyEvent`/`EntityRemovedEvent`.** Both are posted *before* removal (HEAD / before `getEntityIds()`), not after; only `EntityAddedEvent` and `BlockUpdateEvent` are genuinely after-application.
6. **`CrystalAura` "spawn-callback break" cancellation side effect.** Cancelling `doBreak(Entity)` HEAD (the point covering both tick and spawn paths without touching `onEntityAdded`'s bookkeeping) also skips Meteor's `breakTimer`/`removed`/`attemptedBreaks`/`waitingToExplode` updates; whether that leaves the module resumable after the gate lifts is not established by the artifacts. Needs a local single-player smoke test during P2c.
7. **`DamageUtils` fidelity.** Resistance < 600 transparency, hard-coded `12`, and `int` truncation mean predicted damage is not the server's; the direction of error is not bounded by the artifacts.
8. **Bundle application timing.** 1.21.11 `handleBundlePacket` forwards to each sub-packet on the client thread; whether a RETURN hook on `handleBundlePacket` runs before or after each sub-packet's own handler is not pinned by `javap`. The port uses per-sub-packet `ClientPacketListener` RETURN hooks instead (the 26.1.2 design), so no bundle-level after-application hook is needed; bundle membership is recorded at `Connection.channelRead0` HEAD.
9. **Build-82 provenance.** The vendored jar is authenticated only against `vendor/README.md` (a third-party archive, upstream commit `7fc97a87…`), not a live Maven `.sha1` (build 82 is pruned from upstream Maven). This is recorded, not a blocker.
