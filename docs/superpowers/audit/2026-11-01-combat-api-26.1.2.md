Method, in the order it was applied:

1. **Version and artifact authentication.** Fetched `https://piston-meta.mojang.com/mc/game/version_manifest_v2.json` live on 2026-11-01, then each version JSON; compared its `downloads.client`/`downloads.server` size and SHA-1 against the local Loom jars. That is how the byte-identical-method claims (e.g. `EndCrystal.hurtServer`, `PistonMovingBlockEntity.moveEntityByPiston`) were established even where the class hashes differ.
4. **Meteor.** Extracted `meteor-client-26.1.2-20260810.135545-42-sources.jar` to `/tmp/audit/m42` (950 `.java` files) and `meteor-client-26.2-20261009.074120-35-sources.jar` to `/tmp/audit/m35` (944 files); normalised CRLF and `diff -u` the specific files (ConnectionMixin, LocalPlayerMixin, ClientPacketListenerMixin, ClientLevelMixin, LevelChunkMixin, DamageUtils, Rotations, CrystalAura, PacketEvent, event classes). ## 3. Findings

### 3.1 Mapping set, naming differences, and what changed in 26.2

- The target builds with **no explicit mapping dependency**: `26.1.2/build.gradle.kts` declares only `alias(libs.plugins.fabric.loom)`, `26.1.2/gradle.properties` has no `mappings` key, `26.1.2/gradle/libs.versions.toml` pins `minecraft = "26.1.2"`, `jdk = 25`, `meteor = "26.1.2-20260810.135545-42"`, and the Loom cache for 26.1.2 contains no `mappings.tiny`. The version JSONs have no `client_mappings`/`server_mappings` entries. The downloaded jars are already named (`net/minecraft/...`) and the client jar is Mojang-signed, so the effective mapping set is **Mojang names as shipped**, not a Loom-remapped set.
- `net/minecraft/resources/ResourceLocation.class` does not exist in either tree; 26.1.2 already uses `net/minecraft/resources/Identifier`. Any 26.2 code using `ResourceLocation` (if the plan snippets do) must use `Identifier`. The 26.2 audit also records `ResourceKey.location()` → `ResourceKey.identifier()`; the 26.1.2 `ResourceKey` class was not separately audited here, so treat that rename as **UNCONFIRMED** for T1 and confirm at compile time.
- **`EntityTypes` does not exist in 26.1.2.** All entity-type constants are declared on `net.minecraft.world.entity.EntityType` (e.g. `EntityType.END_CRYSTAL`, javap line 54 of `/tmp/audit/et_26.1.2.txt`). 26.2 moved them to `net.minecraft.world.entity.EntityTypes` (`fcc40ed441da13bd`). This is a latent hazard for new `mc` adapters copied from 26.2 vanilla snippets, not a port-wide rename: the 26.2 combat port surface contains no `EntityTypes` reference (the only two occurrences in that tree are the import and `EntityTypes.PLAYER` in `modules/ChatTools.java:84,1164`, outside the port).
- `EntityType` also changed shape beyond the move: T1 has `private final ImmutableSet<Block> immuneTo`, `private static register(ResourceKey,Builder)`, `register(String,Builder)`, `byString(String)`, `vanillaEntityId(String)`; T2 has `private final TagKey<Block> immuneTo`, `PostSpawnProcessor<T>` (replacing the per-entity `Consumer<T>` stack config), `EntitySpawnRequest`, and no `register`/`byString`/`vanillaEntityId`. Code that merely references constants is a rename; code that registers entity types is not portable as-is.
- `net.minecraft.tags.DamageTypeTags` is the real package in both trees (there is no `net/minecraft/world/damagesource/DamageTypeTags.class`). `CommonPlayerSpawnInfo` is in `net/minecraft/network/protocol/game/` (not `world.level`).
- `net.minecraft.advancements.CriteriaTriggers` in T1 vs `net.minecraft.advancements.triggers.CriteriaTriggers` in T2 (`criterion` → `triggers` package move). Off the combat path here, but any copied 26.2 source that references criteria/advancements will need the T1 package.
- `Gui.getChat()` exists in 26.1.2; `Gui.screen()` and `Gui.hud` are the 26.2-only members (`Minecraft.screen` is the T1 field equivalent). The target's own `InventoryWeaponAttack` already uses `mc.screen`; the only `mc.gui.screen()` occurrence in the copied port surface is `core/combat/mc/MinecraftCombatClient.java:255` (26.2 tree).

### 3.2 `LivingEntity.hurtServer` — W, raw-before-mitigation, bypass types, stronger in-window hit

Source of truth: `javap -c -p net.minecraft.world.entity.LivingEntity` from the authenticated 26.1.2 client/merged jars (`LivingEntity.class` is byte-identical in both). The 26.2 audit's C4/C6/C19 are re-verified; the only code-shape change is that 26.2 factors the default knockback into `dealDefaultKnockback`.

Exact T1 `hurtServer(ServerLevel level, DamageSource source, float damage)` control flow, with bytecode offsets:

1. `isInvulnerableTo(level, source)` → return false (0–10). Dead/dying → return false (11–19). `IS_FIRE` + fire resistance → return false (20–41). Sleeping → `stopSleeping()` (42–52). `noActionTime = 0` (53–57).
2. `damage = max(0, damage)` (58–65); save the original in local 4 (66); `ItemStack useItem = getUseItem()` (69); `float blocked = applyItemBlocking(level, source, damage)` (75–82); `damage -= blocked` (84); `itemBlocked = blocked > 0` (89–101).
3. `IS_FREEZING` and `FREEZE_HURTS_EXTRA_TYPES` → `damage *= 5` (103–128). `DAMAGES_HELMET` and a damaged helmet → `damage *= 0.75` (129–163). NaN/Infinite → `Float.MAX_VALUE` (164–180).
4. `boolean flag = true` (181). **Window test (184–193): `invulnerableTime > 10.0f`** — exactly W = 10. If the source has `BYPASSES_COOLDOWN` (196–203), jump to the normal branch.
5. In-window branch: if `damage <= lastHurt` → `return false` (206–216; a weaker or equal hit is rejected, equal included). Otherwise `actuallyHurt(level, source, damage - lastHurt)` (217–226) — the **previous hit's value, which is pre-armour/post-blocking, is subtracted before any mitigation** — then `lastHurt = damage` (229) and `flag = false` (234).
6. Normal branch (240–271): `lastHurt = damage`; `invulnerableTime = 20`; `actuallyHurt(level, source, damage)`; `hurtDuration = 10`; `hurtTime = hurtDuration`.
7. `resolveMobResponsibleForDamage` and `resolvePlayerResponsibleForDamage` (272–282). **If `flag` is false, jump to the end (283: `ifeq 476`)** — the entire post-hit block is skipped: no `ServerLevel.broadcastDamageEvent(this, source)` (321), no `markHurt` (327–348), no knockback gate (352–359), no inlined default knockback (362–476), no `indicateDamage` (the last call, after knockback).
8. If `flag` is true: if `itemBlocked` → `BlocksAttacks.onBlocked(...)` (288–318), else `broadcastDamageEvent` (321); `markHurt()` when the source is not `NO_IMPACT` and (not blocked or `damage > 0`) (327–348); unless `NO_KNOCKBACK`, the default knockback is inlined: for projectiles `calculateHorizontalHurtKnockbackDirection` with a negated pair, otherwise if `source.getSourcePosition() != null` the direction is source-minus-this, and `knockback(0.4, dx, dz)` is called (362–460); then, unless `itemBlocked`, `indicateDamage(dx, dz)` (461–476).

Consequences (all RE-VERIFIED, not inferred from 26.2):

- **W = 10** is a *threshold on the remaining invulnerability counter*, not a duration; the counter is set to 20 on a normal hit and ticks down once per server tick, so the next hit within 10 ticks is in-window and can be stronger, while a hit after 10 ticks is a normal hit.
- **Raw-before-mitigation subtraction**: the value subtracted is the damage after item blocking, freezing and helmet multipliers, but **before armour, enchantment protection, resistance and absorption** (those live in `actuallyHurt`). Phase 0.3's model must apply the same order.
- **No vanilla damage type has `BYPASSES_COOLDOWN`**: `data/minecraft/tags/damage_type/bypasses_cooldown.json` is absent from both the 26.1.2 and 26.2 jars (the 26.1.2 client and merged jars each contain 33 `data/minecraft/tags/damage_type/*.json` entries and the bundled server jar has none; 26.2 has 34, its extra file being `sulfur_cube_with_block_immune_to.json`). Datapacks or mods can populate the tag; the port should treat the tag as dynamic, not hard-code "no bypass".
- **Stronger in-window hit**: it still writes health (and absorption) through `actuallyHurt`, because steps 5/6 call it in both branches, but it skips damage-event broadcast, `markHurt`, hurt sound/animation and default knockback. That is the C6 finding, re-derived from the T1 bytecode. Whether the *target* actually moves zero blocks on 26.1.2 remains a runtime question (§6); the code says no knockback is applied by `hurtServer` on that path.
- `actuallyHurt` order (T1 javap: 10–130): `isInvulnerableTo` → `getDamageAfterArmorAbsorb` → `getDamageAfterMagicAbsorb` (resistance, then protection enchantment) → `max(damage - absorption, 0)` → `setAbsorptionAmount(absorption - (raw - damage))` → absorbed-damage stat (only for `ServerPlayer` sources) → return if damage is 0 → combat tracker / `setHealth(getHealth() - damage)` / hurt effects. For players, `setAbsorptionAmount` writes `Player.DATA_PLAYER_ABSORPTION_ID`; `getHealth`/`setHealth` read and write `LivingEntity.DATA_HEALTH_ID`.
- Damage-type tag contents in T1 (from the merged jar's `data/minecraft/tags/damage_type/`): `bypasses_effects.json` = `[starve]`; `bypasses_enchantments.json` = `[sonic_boom]`; `bypasses_resistance.json` = `[out_of_world, generic_kill]`; `bypasses_invulnerability.json` = `[out_of_world, generic_kill]`; `bypasses_armor.json` includes `on_fire, in_wall, cramming, drown, fly_into_wall, generic, wither, dragon_breath, starve, fall, ender_pearl, …`; `bypasses_shield.json` starts with `#bypasses_armor`. `IS_EXPLOSION`, `NO_IMPACT` and `NO_KNOCKBACK` are behaviour tags used by the paths above.

### 3.3 `CombatRules` mitigation monotonicity

`CombatRules.class` is byte-identical in T1 and T2 (`d06810ecbb0ac127`). The T1 constants are `MAX_ARMOR = 20.0f`, `ARMOR_PROTECTION_DIVIDER = 25.0f`, `BASE_ARMOR_TOUGHNESS = 2.0f`, `MIN_ARMOR_RATIO = 0.2f` (`javap -c` `/tmp/audit/combatrules_t1.txt`).

`getDamageAfterAbsorb(LivingEntity entity, float damage, DamageSource source, float armor, float toughness)`:

```
f          = 2 + toughness / 4
armorRatio = clamp(armor - damage / f, armor * 0.2, 20)
e          = armorRatio / 25
if (source.getWeaponItem() != null && level instanceof ServerLevel)
    e = clamp(EnchantmentHelper.modifyArmorEffectiveness(level, weaponItem, entity, source, e), 0, 1)
return damage * (1 - e)
```

`getDamageAfterMagicAbsorb(float damage, float protection)`:

```
f = clamp(protection, 0, 20)
return damage * (1 - f / 25)
```

**Monotonicity.** For a fixed entity, source, armour and toughness, `armorRatio` is a non-increasing function of `damage` (the term `-damage/f` only lowers it until the `0.2*armor` clamp is reached), so `e` is non-increasing and `1 - e` is non-decreasing. The product `damage * (1 - e)` is therefore **strictly increasing in damage** (both factors are non-decreasing and damage itself grows), including across both clamp boundaries. The magic-absorb step multiplies by the constant `1 - f/25` and the resistance step (inside `getDamageAfterMagicAbsorb(DamageSource, float)`) multiplies by `(25 - (amplifier+1)*5)/25` for resistance I–IV and by 0 for V+; both are constant for a fixed effect state. The only non-constant hook is `EnchantmentHelper.modifyArmorEffectiveness`, which can depend on the weapon's enchantments (not on the damage value in vanilla); a caller that changes the weapon between hits can therefore see a different curve — the plan's P1.2 must hold the source/weapon fixed when it compares the ratio. **Mitigation is nondecreasing in input damage; no inversion was found.**

### 3.4 `ServerExplosion` — entity search, damage, 3-D knockback, block destruction

`ServerExplosion` differs from 26.2 only in the `EntityType`→`EntityTypes` constants (`canTriggerBlocks`, `shouldAffectBlocklikeEntities`); the algorithm is identical. T1 evidence `/tmp/audit/explode_t1.txt`.

**Entity search and damage** (`hurtEntities`):

- `if (radius < 1.0E-5) return;` then **`float f = radius * 2`** (offsets 11–17). For the crystal's power 6 this is **12 blocks**: the entity search box is `floor(center ± (f+1))` on each axis, and each candidate is rejected when `sqrt(distanceToSqr(center)) / f > 1`.
- Candidate position: `entity instanceof PrimedTnt ? entity.position() : entity.getEyePosition()`; direction `= position.subtract(center).normalize()`.
- `shouldDamage = calculator.shouldDamageEntity(...)`; `knockbackMultiplier = calculator.getKnockbackMultiplier(...)`; `seen = (shouldDamage || multiplier != 0) ? getSeenPercent(center, entity) : 0`.
- Damage: `entity.hurtServer(level, source, calculator.getEntityDamageAmount(explosion, entity, seen))`. `ExplosionDamageCalculator.getEntityDamageAmount`: `f = explosion.radius()*2`; `d = sqrt(entity.distanceToSqr(center))/f`; `impact = (1-d)*seen`; `return (impact*impact + impact)/2 * 7 * f + 1` — for power 6, `f = 12`, so the maximum raw damage at point-blank full exposure is `(1+1)/2*7*12 + 1 = 85`.
- Knockback: `resistance = entity instanceof LivingEntity ? getAttributeValue(Attributes.EXPLOSION_KNOCKBACK_RESISTANCE) : 0`; `push = direction.scale((1-d) * seen * knockbackMultiplier * (1-resistance))`; **`entity.push(push)`** applies all three components (x, y and z), so the knockback is genuinely 3-D. Redirectable projectiles get the source entity as owner; players that were hit are recorded; `onExplosionHit(source)` runs at the end. There is no "hole in a wall" exemption — exposure is the only occluder, and it is computed by `getSeenPercent`.
- `getSeenPercent(Vec3 center, Entity entity)`: `xStep = 1/((maxX-minX)*2+1)`, `yStep` and `zStep` analogously; offsets `(1 - floor(1/step)*step) * 0.5`; one ray per sample from the sample point to the explosion centre, clipped against blocks/fluids with `level.clip(...)`; result is the hit fraction. This is the geometry Meteor copies (with its own block filter, see §3.8).

**Block destruction** (`calculateExplodedPositions`):

- 16×16×16 direction grid, but only the shell (`i == 0 || i == 15` on at least one axis) produces a ray; direction normalized.
- Per ray: `intensity = radius * (0.7f + level.random.nextFloat() * 0.6f)`. For power 6 that is **4.2 … 7.8**.
- Step length `0.3` (literal `0.30000001192092896` for x/y/z), then `intensity -= 0.22500001f` after each step.
- At each step: `pos = BlockPos.containing(x,y,z)`; stop if outside world bounds; if the block-resistance lookup is present, `intensity -= (resistance + 0.3f) * 0.3f`; if `intensity > 0 && calculator.shouldBlockExplode(...)` the position is added. Air costs nothing (`getBlockExplosionResistance` returns empty for air with an empty fluid). `shouldBlockExplode` defaults to `true`.
- Therefore a block with resistance ≥ ~14 (e.g. obsidian 1200, stone 6 → `(6.3)*0.3 = 1.89` per block) either survives (obsidian: 4.2–7.8 minus 360.09 goes negative immediately) or is destroyed after enough remaining intensity (stone: 4.2–7.8 minus 1.89 leaves 2.3–5.9, so several blocks along the ray are destroyed). The crystal's `Level.ExplosionInteraction.BLOCK` is what enables this path.

### 3.5 End crystals — placement, damage, explosion-tagged removal, piston push

**Placement** (`EndCrystalItem.useOn`, T1 bytecode; behaviour identical to 26.2 except a local-variable shape): the clicked block must be `Blocks.OBSIDIAN` or `Blocks.BEDROCK`; `above = pos.above()`; `level.isEmptyBlock(above)` must hold; the entity volume `AABB(x, y, z, x+1, y+2, z+1)` must contain no entities; spawn `new EndCrystal(level, x+0.5, y, z+0.5)`, `setShowBottom(false)`, `addFreshEntity`, `GameEvent.ENTITY_PLACE`, dragon-fight respawn if a fight exists, `getItemInHand().shrink(1)`, return `SUCCESS`. Note the placement rule is permissive: only the *first* block above the base must be air; the second block of the crystal's 2-block height is not checked as a block, only entities in the 1×2×1 volume block placement. (C13.)

**Damage** (`EndCrystal.hurtServer`): always returns false for `isInvulnerableToBase` and for an EnderDragon attacker; if not already removed, `remove(RemovalReason.KILLED)`; then:
- if the source **is not** `DamageTypeTags.IS_EXPLOSION`: `damageSource = getEntity() != null ? damageSources().explosion(this, getEntity()) : null`; `level.explode(this, damageSource, null, getX(), getY(), getZ(), 6.0f, false, Level.ExplosionInteraction.BLOCK)`. This is the power-6, block-destroying explosion of §3.4 (radius 6 → entity search 12).
- if the source **is** `IS_EXPLOSION`: no explosion is created; the method goes straight to `onDestroyedBy(level, source)`.

So an explosion-damaged crystal is removed **without a secondary explosion**, while any other damage source (player hit, arrow, etc.) removes it and creates a new power-6 explosion. A chain reaction is therefore possible only through the non-explosion path; crystals caught in another crystal's blast are removed silently. (C14.)

**Piston push**: `EntityType.END_CRYSTAL` is registered with `sized(2.0f, 2.0f)`, `fireImmune()`, `clientTrackingRange(16)`, `updateInterval(Integer.MAX_VALUE)` and category `MISC`, no loot table. `EndCrystal`'s constructor sets `blocksBuilding = true`; it does **not** override `getPistonPushReaction`, so the default `NORMAL` applies. `PistonMovingBlockEntity` pushes it like any non-IGNORE entity: collision AABB → `PistonMath.getMovementArea` → `d2 = min(movement, d) + 0.01d` → `entity.move(MoverType.PISTON, delta)` with the `NOCLIP` ThreadLocal set to the piston direction for the duration of the move (`moveEntityByPiston`). Constants are `TICKS_TO_EXTEND = 2`, `TICK_MOVEMENT = 0.51d`, `PUSH_OFFSET = 0.01d`. Sticky pistons only pull entities matching the sticky criteria (slime/honey), so they do **not** pull crystals back. (C21 re-verified with a T1-specific revision: 26.2 has an extra `Entity.syncPosition` check in `ServerEntity.sendChanges` that T1 does not have — see §3.6.)

**Why position prediction is needed**: `updateInterval(Integer.MAX_VALUE)` means `ServerEntity.sendChanges` syncs the crystal's position on the spawn tick (`tickCount % MAX_VALUE == 0`) and then almost never, unless `entity.needsSync` or the entity data is dirty. Piston movement sets no `needsSync` (only `push`/`load` do). The client therefore cannot rely on entity position updates for a pushed crystal; it must reconstruct the move from the piston block event and the two-tick extension (0.51 per tick plus the 0.01 push offset). The exact client-observed per-tick distance on 26.1.2 is UNCONFIRMED (§6; the 26.2 trace measured 1.02 over two ticks, not the literal 1.04).

### 3.6 Attack handler, server health/absorption tracking, ack, entity status, respawn

**Attack handler** (`ServerGamePacketListenerImpl.handleAttack(ServerboundAttackPacket)`, T1 `javap -c` `/tmp/audit/sgpli_t1.txt`). Gate order:

1. `PacketUtils.ensureRunningOnSameThread`.
2. If the client has not loaded or the player is a spectator, return.
3. `Entity entity = level.getEntityOrPart(packet.entityId())`; `resetLastActionTime()`.
4. If `entity == null` or outside the world border → return.
5. `AABB box = entity.getBoundingBox()`; `ItemStack stack = player.getMainHandItem()`.
6. If `!player.isWithinAttackRange(stack, box, 3.0d)` → return (attack reach gate; 3.0 is the addend).

### 3.10 Hook checklist for the after-application observation layer

## 4. Concise answers (a–l), mirroring the 26.2 audit

**a. Is the cooldown window W = 10 server ticks, and is the earlier hit subtracted raw, before mitigation?**
Yes. In `net.minecraft.world.entity.LivingEntity.hurtServer(ServerLevel, DamageSource, float)` (T1 merged jar, offsets 181–264) the server sets a boolean `flag = true` and enters the in-window branch only when `invulnerableTime > 10` and the damage type does **not** have `BYPASSES_COOLDOWN`. In that branch it compares `damage` with `lastHurt`; if `damage <= lastHurt` it returns false (equal damage is rejected too). Otherwise it calls `actuallyHurt(level, source, damage - lastHurt)` — the subtraction happens on the **raw, post-blocking, pre-armour** value — then sets `lastHurt = damage` and `flag = false`. The normal (out-of-window) branch sets `lastHurt = damage`, `invulnerableTime = 20`, calls `actuallyHurt(level, source, damage)`, and sets `hurtDuration = 10; hurtTime = 10`. So a hit inside the window deals the *difference* between the new raw hit and the previous raw hit; armour, resistance and protection are then applied by `actuallyHurt` (§3.2), and the extra damage is not added to `lastHurt` (the new raw value replaces it).

**b. Does any vanilla damage type bypass the cooldown?**
No. `data/minecraft/tags/damage_type/bypasses_cooldown.json` is **absent** from both the 26.1.2 and 26.2 jars (the 26.1.2 client and merged jars each contain 33 tag JSON files and its bundled server jar contains none; 26.2 has 34, the only extra file being `sulfur_cube_with_block_immune_to.json`). The `DamageTypeTags.BYPASSES_COOLDOWN` field exists in `net.minecraft.tags.DamageTypeTags`, but the tag is empty by default. Datapacks and mods can populate it; that is the only way to bypass the window in vanilla data. `bypasses_cooldown` is therefore not a usable vanilla exception path.

**c. What does a stronger in-window hit do beyond health?**
For a non-bypassing hit inside the window, after the `actuallyHurt` call at offset 217 the method sets `flag = false` (offset 234) and at offset 283 `ifeq 476` jumps over the whole post-hit block: it does **not** call `ServerLevel.broadcastDamageEvent` (offset 321), does **not** call `markHurt` (327–348), and does **not** run the default knockback block (362–476), which is where `indicateDamage` and the hurt animation/sound path live. Health and absorption are updated because they are written by `actuallyHurt`/`setAbsorptionAmount` (health metadata and, for players, `DATA_PLAYER_ABSORPTION_ID`). It also does not set `hurtTime`/`hurtDuration` (those are set only on the normal branch). Net effect: health/absorption metadata changes, no damage-event broadcast, no hurt animation/sound, no default knockback. This is re-verified statically; the 26.2 audit's runtime trace (§8 there) is still the evidence that no target movement occurs, and no equivalent 26.1.2 trace exists (see §6).

**d. Is damage monotone in the input under `CombatRules`?**
Yes, for fixed armour/toughness/protection and source. `getDamageAfterAbsorb` computes `f = 2 + toughness/4`, `armorRatio = clamp(armor - damage/f, armor*0.2, 20)`, `e = armorRatio/25`, then `damage * (1 - e)` (with an optional `EnchantmentHelper.modifyArmorEffectiveness` clamp when the source has a weapon item). As input damage rises, `armorRatio` is non-increasing (it falls linearly until the `armor*0.2` floor, then stays), so `e` is non-increasing and the output is non-decreasing; the function is continuous at the clamp boundary because the clamp is a max/min of continuous pieces. `getDamageAfterMagicAbsorb` applies `damage * (1 - clamp(protection, 0, 20)/25)`, a constant factor. The division `damage/f` means the mitigation percentage shrinks as the hit grows, which is the "burst beats armour" geometry the plan relies on; there is no interval where a larger hit deals less damage.

**e. Does a power-6 crystal blast that is tagged `is_explosion` remove the crystal without a secondary explosion?**
Yes. `EndCrystal.hurtServer` (T1, offsets 22–103) first `remove(RemovalReason.KILLED)`, then `if (!source.is(DamageTypeTags.IS_EXPLOSION))` builds a damage source (`damageSources().explosion(this, source.getEntity())` when there is an attacker, else null) and calls `level.explode(this, damageSource, null, getX(), getY(), getZ(), 6.0f, false, Level.ExplosionInteraction.BLOCK)`. An explosion-tagged hit skips that call, so the crystal is removed with **no** second explosion; `onDestroyedBy(level, source)` still runs. A hit with a non-explosion source does explode (power 6, block destruction).

**f. How far does the explosion search, and is the knockback 3-D?**
`ServerExplosion.hurtEntities` uses `float f = radius * 2` (offset 11–17), so a power-6 crystal searches a 12-block radius; the AABB is `floor(center ± f ± 1)` on each axis and `level.getEntities(source, aabb)` is filtered per entity by `d = sqrt(distanceToSqr(center)) / f; if (d > 1) skip`. The direction is the normalised **3-D** vector from the explosion centre to `entity.getEyePosition()` (or `entity.position()` for primed TNT), and `entity.push(dir.scale((1-d) * seen * knockbackMult * (1 - resistance)))` includes the Y component. `seen` comes from `getSeenPercent`, which ray-clips the entity's bounding box; there is no per-block "hole exemption" for the blast direction itself, but cover does reduce `seen` (blocked samples reduce both damage and knockback). No line-of-sight check gates whether an entity is searched.

**g. What exactly does crystal placement require?**
`EndCrystalItem.useOn` (T1): the clicked block must be `Blocks.OBSIDIAN` or `Blocks.BEDROCK`, else FAIL; `above = pos.above()` must satisfy `level.isEmptyBlock(above)`, i.e. the first block above the base must be strictly air (a fluid fails); the entity volume `AABB(x, y, z, x+1, y+2, z+1)` must contain no entities (`level.getEntities(null, aabb)` empty), which is the 1×2×1 volume; on the server it spawns `new EndCrystal(level, x+0.5, y, z+0.5)`, `setShowBottom(false)`, `addFreshEntity`, fires `GameEvent.ENTITY_PLACE`, calls `getDragonFight().tryRespawn()` when a fight exists, then shrinks the item by 1 and returns SUCCESS. It does not check the second block for air separately (the entity AABB covers the 2-block height).

**h. Which attacks does the server disconnect for?**
`ServerGamePacketListenerImpl.handleAttack` (T1) disconnects with `multiplayer.disconnect.invalid_entity_attacked` and logs `"Player {} tried to attack an invalid entity"` when the target is an `ItemEntity`, an `ExperienceOrb`, the player itself, or an `AbstractArrow` whose `isAttackable()` is false (offsets 118–158). Before that it requires `hasClientLoaded && !isSpectator`, `level.getEntityOrPart(id)` non-null and inside the world border, `player.isWithinAttackRange(mainHandItem, entity.getBoundingBox(), 3.0d)`, and not `stack.has(DataComponents.PIERCING_WEAPON)`; after the disconnect gate it requires `stack.isItemEnabled(level.enabledFeatures())` and `!player.cannotAttackWithItem(stack, 5)`, and only then calls `player.attack(entity)` (offset 217). Note this is `handleAttack`, not `handleInteract`.

**i. How are health and absorption tracked and sent by the server?**
They are two different fields. Player health is `LivingEntity.DATA_HEALTH_ID` (a `SynchedEntityData` accessor; statically id 9 from `Entity` 0–7 and `LivingEntity` flags=8, health=9) and absorption is `Player.DATA_PLAYER_ABSORPTION_ID` (Player's first accessor; statically id 15 by the same derivation — see §6 for the 26.2 audit's id-17 trace discrepancy). Both are written through `setHealth`/`setAbsorptionAmount`, and `ServerEntity.sendDirtyEntityData()` (T1, offsets 56/29) packs the dirty values and sends `new ClientboundSetEntityDataPacket(entity.getId(), packedItems)` to tracking players **and self**; this is not tied to a damage event. In addition, `ServerPlayer.doTick()` compares `getHealth() != lastSentHealth || lastSentFood != foodData.getFoodLevel() || ((foodData.getSaturationLevel()==0) != lastFoodSaturationZero)` and, when true, sends a separate `ClientboundSetHealthPacket(getHealth(), food, saturation)` (fields `lastSentHealth`/`lastSentFood`/`lastFoodSaturationZero`). The client applies the health packet through `LocalPlayer.hurtTo` (not `setHealth`), and metadata through `assignValues`. So a single damage tick can produce both a health packet and an entity-data packet; the one-packet obligation in C19 is **UNCONFIRMED** for 26.1.2, and the ordering of the two is not established by the artifacts.

**j. Is Meteor's `PacketEvent.Receive` before or after vanilla, and on which thread?**
Before vanilla, on the Netty thread. Build 42 `ConnectionMixin.java:46-54` injects at the `INVOKE` of `Connection.genericsFtw` with `shift = BEFORE`, so Receive is posted before the packet is decoded/dispatched and before `PacketUtils.ensureRunningOnSameThread` moves it to the client thread. For `ClientboundBundlePacket` it iterates `subPackets()` and posts one Receive per sub-packet, removing cancelled ones; the bundle wrapper is not posted. It is cancellable, so it cannot represent applied state (C9). `DamageUtils` is unaffected by this: its `HIT_FACTORY` (line 66) treats blocks with `getExplosionResistance() < 600` as transparent, and its `RaycastFactory` is public, so a custom (vanilla-faithful) exposure policy can be plugged in without forking Meteor; its damage is cast to `int` at line 97 and hard-codes the `12` factor.

**k. What does Meteor's `CrystalAura` send, and when?**
Build 42: on the attack path, line 838–843 computes yaw/pitch and, when steps are needed, `Rotations.rotate(yaw, pitch, 50, () -> attackCrystal(crystal))`, otherwise line 850 calls `attackCrystal(crystal)` directly; `attackCrystal` (line 870) optionally swings and **directly** sends `new ServerboundAttackPacket(entity.getId())` at line 872 (`mc.player.connection.send`, no `startPrediction`). On the place path, lines 983–988 rotate with the same priority and callback `placeCrystal(...)`, else call directly; `placeCrystal` (line 1021) sends via `mc.gameMode.startPrediction(mc.level, sequence -> new ServerboundUseItemOnPacket(hand, result, sequence))` at line 1038, then optionally swings, sets `placing`/`placingTimer=4`/`kaTimer=8` and `placingCrystalBlockPos` (line 1046). `doYawSteps` (line 1103) queues a `-100`-priority rotation; `onPreTickLast` (line 715) also queues one to restore; `tick` line 707 calls `doPlace()` only when no rotation happened this tick. There is also a **spawn/fast-break path**, and it is real (it is the 26.2 audit's "spawn-callback break", not Comet-side code): `onEntityAdded(EntityAddedEvent)` (lines 720–731) keeps its `placing`/`placedCrystals` bookkeeping (lines 722–726) and then, when `fastBreak` is on, no rotation happened this tick, and the attack budget allows, calls `doBreak(event.entity)` at line 731; `doBreak(Entity)` (line 814) performs the optional anti-weakness `InvUtils.swap` (line 825, `setSelectedSlot` + `meteor$syncSelected()` → `ensureHasSentCarriedItem()`, a carried-item send path) and then the same `attackCrystal` send (directly at line 850, or through the line 843 rotation callback). So a tick can send from `doBreak()` (line 759 → 777) **or** from `onEntityAdded` → `doBreak(Entity)`, and both funnel through `attackCrystal` (line 870 → 872); the place path always funnels through `placeCrystal` (line 1021 → 1038). Suppression therefore needs the full 26.2 surface, not two cancels: eight HEAD cancels (`onPreTick`, `onPreTickLast`, `doBreak()V`, `doBreak(Entity)`, `attackCrystal`, `doPlace()`, `placeCrystal`, `doYawSteps`→false), both `Rotations.rotate(DDILjava/lang/Runnable;)V` `@Redirect`s wrapping `CrystalCombatGate.guard`, and `protects(UUID)` on `doBreak(Entity)`/`attackCrystal` regardless of activation. The reason is the queued-callback hazard: `Rotations.rotate` only enqueues, and callbacks run later in `onSendMovementPacketsPost` (line 131), so a callback queued before suppression still reaches `attackCrystal`/`placeCrystal` after it; cancelling an entry method stops only new callbacks. `placeCrystal` HEAD is the place-side cancel point — the direct line-993 branch and the line-1069 self-recursion both funnel through it, whereas a callback-only guard would let both send `ServerboundUseItemOnPacket`/swing. Do **not** cancel `onEntityAdded` (bookkeeping 722–726). `doPlace()` never sends and never rotates; the delayed placement rotate is in `lambda$doPlace$1` (line 988), registered by `BlockIterator.after` at line 971.

**l. Do the Comet helpers send packets, and who owns what?**
`InventorySlotLoan.prepare()` **can send** (`restore()`/`borrow()` call `handleContainerInput(..., ContainerInput.SWAP, ...)` at lines 83/130), and `InventoryWeaponAttack` sends when its tick gate fires (`mc.gameMode.attack` + `swing` at lines 90–91); `Speedmine.requestBreak` **can send** (`handleBlockClick` → `sendStart` → `ServerboundPlayerActionPacket.START_DESTROY_BLOCK`) and has no cancellation token or ownership check; `ScaffoldCoordinator` only observes/queues (it does not itself send) but its `prediction`/`legacyPlacement`/`guardLegacyRotation` paths wrap code that may send; `PlacementTracker`, `ServerPacer` and `PacketBudget` are pure. Ownership as in the 26.2 audit: Meteor owns the offhand slot and the rotation queue; the scaffold adapter only injects a rotation immediately before vanilla's first yaw read, refuses while `Rotations.rotating` or the accessor queue is non-empty, and restores the visual rotation in `finish`. The port must not call `prepare()`, `Speedmine.requestBreak` or the `InventoryWeaponAttack` tick from a path where a send is forbidden (C17).

## 6. Residual uncertainty

1. **Absorption metadata id.** The 26.2 audit §8 reports an observed `ClientboundSetEntityDataPacket` carrying health id 9 and absorption id 17. Static derivation from the pinned jars (identical `ClassTreeIdRegistry` and identical per-class accessor counts in T1 and T2: `Entity` 8, `LivingEntity` 7, `Player` 4) gives absorption id **15** in both versions. Two accessors are unaccounted for in the 26.2 trace, which may have run with an extra mixin/accessor or a different build. The numeric id is therefore **UNCONFIRMED**; the port must key on `LivingEntity.DATA_HEALTH_ID`/`Player.DATA_PLAYER_ABSORPTION_ID` objects, never literals.
2. **Runtime behaviour of the stronger in-window hit in 26.1.2.** The static bytecode is unambiguous (no broadcast/markHurt/knockback, health+absorption still written), but no 26.1.2 trace was recorded (the plan's Phase 0.4 traces are for 26.2). The 26.2 trace shows zero target movement; the 26.1.2 motion model should be validated before relying on "no knockback" (safety-relevant).
3. **Server packet ordering for self damage.** `ServerEntity.sendDirtyEntityData()` and `ServerPlayer.doTick()` can both emit packets in the same tick; the relative order of `ClientboundSetEntityDataPacket` (health/absorption) and `ClientboundSetHealthPacket` was not established from bytecode. The one-packet obligation (C19) remains unconfirmed for 26.1.2.
4. **Piston displacement per tick.** The formula is `TICK_MOVEMENT = 0.51` plus `PUSH_OFFSET = 0.01` per collision pass; the 26.2 trace measured 1.02 blocks over two ticks (0.51/tick), where the literal formula predicts 1.04. The 26.1.2 constants are identical (`PistonMovingBlockEntity`, hash differs only in `BlockEntityTypes.PISTON`), but actual per-tick displacement in 26.1.2 was not traced.
5. **Meteor event timing claims for `EntityDestroyEvent`/`EntityRemovedEvent`.** Both are posted *before* removal (HEAD / before `getEntityIds()`), not after; the 26.2 audit's summary calling them "after-application" is imprecise, and the port must not use them as applied-state hooks.
6. **`CrystalAura` "spawn-callback break" is real, but the cancellation side effect is untraced.** Build 42 `onEntityAdded` (lines 720–731) calls `doBreak(Entity)` (line 814) when `fastBreak` is on, which reaches the `attackCrystal` send (lines 843/850 → 872); this is the send path the 26.2 audit's §3.8.3 and the plan's P2c suppression target. The structural requirement is the full surface in §3.8: `doBreak(Entity)` HEAD alone is not enough, because a rotation callback queued before suppression still fires later — `attackCrystal` HEAD and both `Rotations.rotate` redirects are also required. The remaining uncertainty is behavioural, not structural: cancelling `doBreak(Entity)` at HEAD (the only point that covers both the tick and spawn paths without touching `onEntityAdded`'s placing/placedCrystals bookkeeping) also skips Meteor's `breakTimer`/`removed`/`attemptedBreaks`/`waitingToExplode`/break-render updates, and whether that leaves `CrystalAura`'s internal state consistent enough for the module to resume after the gate lifts is not established by the artifacts. It needs a local (single-player) smoke test during P2c; no server may be contacted.
7. **`DamageUtils` fidelity.** Its exposure policy (resistance < 600 transparent), hard-coded `12`, and `int` truncation mean predicted damage is not the server's; the direction of error is not bounded by the artifacts.
8. **Mappings.** There is no mappings artifact to verify against: the tree consumes the Mojang-named jar. Any name comparison with 26.2 is a class-name comparison, not a mapping comparison.
